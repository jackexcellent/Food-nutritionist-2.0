# 流程圖對比分析

## 📊 您的原始流程圖 vs 實際架構

### 🔴 原始流程圖的問題

```
使用者輸入 → VLM → USDA → ✓ → Retriever → 歷史對話記錄
                     ↓              ↓
              Coordinator ← ─────────┘
                     ↓
                   LLM
                     ↓
                 回應輸出
```

**主要問題**:

1. ❌ 缺少 **TFND** (台灣食品資料庫) - 這是主要資料源
2. ❌ 缺少 **資料庫存儲層** - 資料如何持久化？
3. ❌ USDA 位置不對 - 不是在 VLM 之後，而是在營養查詢階段
4. ❌ Coordinator 角色模糊 - 實際有多個協調器
5. ❌ LLM 功能不完整 - 除了推薦，還用於熱量估算
6. ❌ Retriever 輸入來源不清楚 - 應該從資料庫讀取

## 🎯 關鍵修正點

### 1. **營養資料查詢流程**

**錯誤理解**:

```
VLM → USDA → Retriever
```

**正確流程**:

```
VLM → 營養查詢協調器 → 資料庫
        ├─ TFND (優先)
        ├─ USDA (備用)
        └─ LLM (最後)
```

### 2. **資料持久化**

**缺少的層**:

```
營養資料 → [❌ 缺少存儲層] → Retriever
```

**實際流程**:

```
營養資料 → SQLite Database → Retriever
            (持久化存儲)
```

### 3. **Coordinator 角色**

**您的理解**: 一個 Coordinator 處理所有事情

**實際架構**: 兩個專門的協調器

- **NutritionCalculator**: 協調 TFND/USDA/LLM 查詢
- **RecommendationEngine**: 協調 RAG 和 LLM 生成

### 4. **LLM 的雙重角色**

**您的理解**: LLM 只用於生成推薦

**實際功能**:

1. **熱量估算** (NutritionCalculator 中)
   - 當 TFND 和 USDA 都找不到時
   - 使用 AI 估算未知食物的熱量
2. **推薦生成** (RecommendationEngine 中)
   - 基於歷史資料生成個人化建議
